# Opt-in report receiver — local candidate, NOT deployed

This is the only proposed publisher data flow. Normal conversations still go
directly to the user's gateway. A user must select a response, review/redact it,
choose a reason, and explicitly submit. No audio, prior messages, gateway URLs,
credentials, device/account identifiers, analytics, or diagnostic attachments are accepted. A random per-report reference supports receipts and retries.

## Contract

`POST https://voxkin.builderofthings.studio/api/reports`

Content-Type `application/json`. Exactly four string fields:

```json
{"reportId":"55be6394-40bd-4cc4-a781-ed5a6f984677","response":"Selected text, optionally redacted entirely","reason":"other","note":""}
```

- `reportId`: canonical lowercase UUID generated by the client for one submission.
- `response`: 0–12000 UTF-16 code units, allowing complete redaction.
- `reason`: `harmful`, `hate`, `sexual`, `inaccurate`, or `other`.
- `note`: 0–2000 UTF-16 code units. Use an empty string when omitted in the UI.
- Raw request maximum 200000 bytes; duplicate/extra keys, malformed Unicode,
  compressed bodies and chunked requests are rejected.
- 201 new or 200 identical duplicate: `{"reportId":"matching-uuid"}`.
- 409 conflicting reuse of a UUID; 400/411/413/415 invalid request, 429 throttled,
  503 unavailable/full. Error bodies are generic and never echo content.
- Client must not claim delivered until receipt validates. Network errors can
  happen after commit: explicit retry uses the same frozen payload and UUID.
  No automatic retries. An expired/deleted UUID may be accepted anew after purge.

## Implementation and limits

Python 3.10+ standard library, SQLite, loopback-only port8793. Maximum16 concurrent
handlers with10second socket timeout. No user account/token is appropriate for
this public opt-in action; do not embed a shared secret in the app.

Three attempts/minute and ten/hour per direct peer IP. Caddy overwrites the
dedicated IP header from its actual remote address; do not expose the loopback
port or forward arbitrary client headers. A CDN/proxy in front needs a separately
reviewed trusted-proxy configuration (otherwise all users share its bucket).
Rate limiting hashes IPs using a process-random salt, holds at most4096 buckets
in memory, and expires them after an hour. It stores no IPs in the database or
logs. Restart resets these best-effort buckets; distributed abuse can still hit
the global storage bound. Maximum10000 retained reports, then truthful503.

SQLite commits before acknowledgement. Reports are retained for up to30days in
the running service, purged on startup, every30seconds, and before accepting
reports or triaging. Boundary deletion can lag by the30second sweep. If the host
is offline, deletion runs before service resumes; do not promise offline disks
are erased on schedule. Duplicate retries do not extend original retention.
`secure_delete=ON` overwrites deleted main-database content and rollback journals
are deleted after transactions; there is no WAL archive. This is logical
application deletion, not a guarantee about SSD wear-leveling or host snapshots.

## Deployment gate (operator checklist, not executed)

1. Obtain production approval bound to the final immutable source. Inspect the
   actual Voxkin host and existing Caddy site; do not modify other sites.
2. Confirm Linux/Python/systemd support, encrypted private storage, available
   disk space, and **exclude `/var/lib/voxkin-reports` from backups/snapshots**.
   If the host cannot exclude it, stop and define a truthful backup deletion
   policy before collecting any report. Database is private0700 directory/0600
   file; do not move it into the static site's document root.
3. Install `server.py` under root-owned read-only `/opt/voxkin-reporting/` and
   `voxkin-reports.service` as a systemd unit. DynamicUser and StateDirectory
   isolate the receiver; no elevated runtime account or package installation.
4. Merge only `caddy-route.candidate` into the existing hostname block; validate
   full config before reload. Ensure proxy/access/security tooling does not log
   report bodies, query strings or IPs for this endpoint. The app sends no query
   strings and the service rejects paths with them. Retain no request-body
   captures in support tooling. Keep local port unreachable externally.
5. Activate only after privacy wording, Data Safety answers and operator triage
   ownership match actual deployment. Verify HTTPS with synthetic content,
   duplicate delivery, invalid payload, and unchanged static site/other services.
6. Verify the service starts after reboot, monitors availability/restarts and
   disk capacity without body logging, and expiration works on the host using a
   synthetic aged row. Monitor last successful purge externally if changing the
   runtime. A purge failure terminates the process; restart purges before serving.
7. Test rollback: disable only this report route/service; app must display
   failure, not successful submission. Preserve encrypted retained data for
   triage/deletion; disabling the service also stops periodic sweeps, so the
   operator must run `triage.py purge` until removal/retention is complete.

No DNS, production route, service, database, report, deployment or availability
claim is created by this source directory. Caddy/systemd syntax still needs
validation against the target installed versions.

## Restricted triage and deletion

Owner: Builder of Things Studio operator. Before launch, assign a real review
cadence (recommended each business day); code cannot establish a staffed review
process. Only authorized host operators may read reports. Do not copy report
content to issue trackers, AI agents, email, shared chats or external services.

Install `triage.py` beside `server.py`. Run locally on the host with authorized
access to the state directory (e.g. sudo); never expose an admin HTTP route.

```sh
python3 /opt/voxkin-reporting/triage.py list
python3 /opt/voxkin-reporting/triage.py show REPORT_UUID
python3 /opt/voxkin-reporting/triage.py reviewed REPORT_UUID
python3 /opt/voxkin-reporting/triage.py delete REPORT_UUID
python3 /opt/voxkin-reporting/triage.py purge
```

`list` shows only receipt/date/status (latest100). `show` deliberately prints
selected report content as escaped JSON to prevent terminal-control injection;
use a private terminal without session recording, avoid redirecting to retained
logs, and clear scrollback afterward. `reviewed` records status only and does not
extend retention. Record any resulting remediation without reproducing submitted
content. For a user's deletion request, use their report reference; no identity
tracking was collected to find it otherwise. Report review is not emergency
response and cannot itself change a user's independently operated gateway model.

## Local tests

```sh
cd ops/reporting
python3 -m unittest -v test_reporting.py
```

Five tests cover exact schema/redaction/UTF-16 limits, durable receipts and
idempotency/conflict, expiration unaffected by duplicate attempts, transient
rate limiting, and live loopback HTTP status/receipt/body bounds/no read route.
They use temporary databases and fictional content only. Target-host TLS,
systemd, Caddy and operator procedures remain deployment qualification work.
